I am building an open-source browser testing and product-analysis application for NOVA, a six-hour hackathon. Refine its graph algorithm into a precise, implementable design. Treat this as both algorithm design and an adversarial correctness review.
I value correctness, clear assumptions, measurable usefulness, and a working implementation over impressive terminology. Challenge weak premises. Do not declare an approach novel, optimal, safe, or statistically reliable without establishing the conditions that make that claim valid. Do not give me a long menu of techniques without choosing a coherent algorithm.
No implementation or performance result should be assumed to exist already.
The product should let a developer provide:
- An application URL, including localhost.
- A task or longer-term objective.
- Starting conditions, allowed actions, and success criteria.
- Metrics such as clicks, completion, latency, reproducible failures, or keyboard accessibility.
- Optional competitor URLs.
- An inference provider: a strong cloud model, a compatible custom endpoint, or local Qwen 27B at 8-bit.
It should:
- Perform bounded reconnaissance with deterministic crawlers and inexpensive interpretation.
- Learn a partial graph of meaningful application states and observed actions.
- Direct expensive reasoning toward useful unresolved questions.
- Adapt exploration to the selected objective.
- Reduce redundant browser actions and model processing.
- Verify candidate workflows and suspected failures.
- Produce interactive workflow graphs, evidence, comparisons, and recommendations.
The polished interface begins with guided setup and becomes a dashboard with preset widgets. The graph should visibly grow, change priorities, defer branches, reactivate branches, and highlight verified routes. Clicking a graph element should open its observations and evidence.
Users review, edit, and select recommendations. Coding-agent handoff occurs only after the user explicitly authorizes the selected implementation scope. After implementation, the same task can be rerun. This is downstream context, not the algorithm's main implementation burden.
The actual runner, graph engine, and dashboard should be self-hostable. A required proprietary testing backend is outside the intended design. Model inference and hardware are still real costs.
Resources:
- Six hours for a useful hackathon submission, with cumulative working versions.
- Three independent workstreams: backend, UI, and evaluation/presentation.
- Ample development-model access. Runtime efficiency must still be evaluated under controlled budgets.
- Cloud inference for the primary presentation.
- Local Qwen support as a portability target; do not assume equivalent browser-task performance.
- Existing browser infrastructure such as Playwright may be reused.
- Background resource-aware scheduling is deferred.
- Native mobile/desktop automation is outside the first browser implementation.
Concentrate on a small algorithm module with a stable interface. Do not design an entire frontend or a general agent framework.
The main initial mode is:
Given an application, explicit starting conditions, a goal predicate, and an evaluation budget, find a verified feasible workflow with low user-interaction cost while spending as little investigation computation as practical.
For example:
- Start logged out, with an empty cart.
- Add a specified product and reach a specified checkout milestone.
- Find a shorter valid workflow under the allowed interaction model.
- Compare it with an equivalent competitor workflow.
Success could mean reaching the checkout form or completing a test order. These are different tasks. Do not leave the terminal predicate ambiguous.
Separate:
1. The cost of a user's workflow.
2. The cost of discovering, interpreting, and verifying that workflow.
Do not combine clicks, dollars, latency, and uncertainty in an arbitrary unnormalized weighted sum. Recommend an explicit constrained, lexicographic, or multiobjective formulation, and explain why it suits the first implementation.
Define what counts as an allowed user action. Do not obtain a fictitious zero-click workflow by jumping to URLs, setting internal state, invoking private APIs, or injecting JavaScript in ways excluded by the task. Fixture resets may be available for testing, but are not consumer workflow steps; account for their evaluation cost separately. Preserve underlying action counts when collapsing workflows into macros.

Let U be the cost of an incumbent verified route under specified conditions. For a particular executed or valid candidate prefix p, g(p) is its known cost and h_lower(p) is a justified lower bound on completion cost.
Explain when the rule
g(p) + h_lower(p) >= U
allows excluding extensions of that prefix when seeking a strictly shorter solution. State the deterministic, feasibility, nonnegative-cost, and bound assumptions needed. Explain why this is not a general license to permanently remove its final abstract node.
Address these traps explicitly:
- An LLM relevance judgment is not automatically an admissible heuristic.
- A shortest known distance in an incomplete graph need not lower-bound the true application distance.
- No observed route to the goal does not imply actual unreachability.
- A discovered shortest prefix is not necessarily the true shortest prefix.
- A new transition or shorter arrival history can change a node's relevance.
- Merged states can invalidate otherwise plausible graph arguments.
- A single successful stochastic trial does not establish a reliable route or an expected-cost bound.
If using an optimistic shortest-path lower bound L, explain when L <= C* <= U is valid. In particular, distinguish a complete candidate graph with valid optimistic edge bounds from a graph that omits unknown transitions.
Explain what additional assumptions would justify a certificate, an epsilon-suboptimal result, or a probability statement. If those assumptions are absent, return a scoped claim such as best verified route found under this budget.
Heuristic stopping is allowed, but must not be presented as proof that no better route exists.
